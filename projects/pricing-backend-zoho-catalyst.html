The problem

This project is the shared back end behind two pricing widgets that live inside Zoho CRM, plus a standalone web client that works as a pricing simulator outside the CRM.

The API stores a "salary cheat sheet": typical salary ranges per role and seniority level, with a usage counter that makes the most commonly priced roles float to the top. The widgets read the sheet to suggest salary ranges and write back to it whenever a price is saved, so the data improves with use.

The constraints:

  • Two separate CRM widgets needed one source of truth for role and salary data.
  • The widgets run on Zoho Sigma, a different origin from Catalyst, and carry no Catalyst session. That rules out normal Catalyst authentication for them.
  • A new standalone web client needed a real authentication wall, without breaking the widgets that depend on the open endpoint.
  • Writes needed protection even though the calling pages are public and cross-origin.

The solution

Split the API into two functions with different security postures, so each client gets the strongest protection its platform constraints allow.

How it works

Cheat sheet API

  • GET / returns all rows ordered by Counter descending, so the most frequently priced roles come first.
  • POST /upsert matches on Role plus Seniority. If a row exists, it increments Counter, refreshes UpdatedDate and updates salary values if sent. If not, it inserts a new row with Counter = 1. This is what the widgets call on save, so new roles appear and popular roles rank higher automatically.
  • POST /increment is a legacy route that bumps a counter by row ID. It is kept for backward compatibility and reads the current value server-side rather than trusting the client.

Data model

SalaryCheatSheet: Role, Country, Seniority, MinSalary (int), MaxSalary (int), Counter (int), UpdatedDate (date, YYYY-MM-DD), ROWID.

Web client (manual mode)

A standalone, Catalyst-hosted copy of the pricing simulator with no CRM integration. It is a read-only calculator:

  1. Seniority: pick one of five levels (Entry, Junior, Mid-level, Senior, Team Lead), which sets salary defaults and filters the cheat sheet.
  2. Role lookup: the top five roles for that level appear as quick-pick pills, with a search box for all roles. Selecting a role shows its typical salary range with an "Apply to sliders" button.
  3. Salary and margin: sliders for the salary low end, high end and target margin. Client prices update live for both ends of the range, using a cost multiplier that covers employer costs, a minimum margin floor and prices rounded up to a fixed step.
  4. Data quality rule: a role's range is only offered when it has been recorded at least 3 times and updated within the last 6 months. Otherwise the UI shows "Not enough data for this role, enter manually".

Auth guard on the client

The client checks the Catalyst Hosted Login session with the Web SDK and redirects anonymous visitors to the login page. This is a UX layer only. The real boundary is the server-side Security Rule on cheatsheet-read.

Engineering highlights

01

Two-function security split

Instead of forcing one security model on every client, the API is divided into a public function for cross-origin widgets and an authenticated read-only function for same-origin use. Neither choice weakens the other.

02

Designing around a platform constraint

Catalyst's gateway answers CORS preflight (OPTIONS) requests itself, without CORS headers. So the write key travels in the body and writes go as text/plain, keeping the request "simple" and skipping the preflight.

see the code →
03

Honest threat modelling

The shared key lives in widget HTML, so it is visible in DevTools. The docs state plainly that this is obscurity, not authentication: it deters drive-by writes, and the body-key check is the real server-side gate.

04

Fail closed

If the WIDGET_KEY environment variable is missing, write routes return a clear 500 instead of a 401 that would look like a client-side key mismatch.

see the code →
05

No secrets in source

The server key is read from a per-environment variable. The published widget source keeps a placeholder, and the README documents a full key rotation procedure.

06

Strict CORS allowlist

Instead of *, the function echoes the origin only for Zoho domains, matching on exact host or suffix, and logs rejected origins to make misconfiguration easy to diagnose.

see the code →
07

Injection-safe queries

Single quotes in ZCQL string values are escaped, and row IDs are validated as numeric before use.

see the code →
08

Server-side truth

Counters are read and incremented on the server, never taken from the client.

09

Read-only by construction

cheatsheet-read has no write routes at all, and any other request returns 404, so even a misconfigured Security Rule cannot expose writes through it.

see the code →
10

Documented operational gotchas

Security Rules are console-managed and per environment, new functions default to optional auth, the hosted client name is locked to its first registration, and Data Store rows don't travel with a production promotion.

const ALLOWED_ORIGIN_SUFFIXES = [
  '.zappsusercontent.com',   // Sigma widget hosting
  '.zohostatic.com',
  '.zoho.com', '.zoho.eu', '.zoho.in', '.zoho.com.au', '.zoho.jp', '.zohocloud.com',
];

function originAllowed(origin) {
  if (!origin) return false;
  try {
    const host = new URL(origin).hostname;
    return ALLOWED_ORIGIN_SUFFIXES.some(function (s) {
      return host === s.slice(1) || host.endsWith(s);
    });
  } catch (e) { return false; }
}

function csSufficient(row) {
  if (!row || parseInt(row.Counter) < 3) return false;
  var sixMonthsAgo = new Date();
  sixMonthsAgo.setMonth(sixMonthsAgo.getMonth() - 6);
  return new Date(row.UpdatedDate) >= sixMonthsAgo;
}

Deployment & operations

  • Catalyst project bound through .catalystrc with Development and Production environments.
  • catalyst.json declares the client source and both function targets, so one catalyst deploy ships the client and functions together. Partial deploys are supported with --only functions, --only functions:cheatsheet-read and --only client.
  • The cheatsheet-read Security Rule ({ "methods": ["GET"], "authentication": "required" }) is console-managed and must be set once per environment after the first deploy.
  • Promotion to production carries code and metadata but not Data Store rows, so data is migrated with catalyst datastore:export and :import --production.
  • Deploy order matters: roll out the function and the new widget builds together, then hard-refresh the CRM.

Status & next steps

  • Currently deployed to the development environment only.
  • Production promotion requires setting the Security Rule on cheatsheet-read, setting WIDGET_KEY for the production environment and migrating Data Store rows.
  • Possible future work: per-tier margin floors (the code keeps a separate entry per tier for this purpose), and same-origin hosting of the widgets to replace the shared-key model with real per-user authentication.
